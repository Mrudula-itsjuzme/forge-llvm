# Forge v3 evidence report

## Executive summary

Forge v3 is an evidence-driven LLVM 18 optimization toolkit, not a claim of a
new general-purpose optimizer. It combines three deliberately narrow passes
with structured diagnostics, configurable schedules, a schema-versioned
experiment registry, differential and mutation testing, an Alive2 bridge,
static multi-architecture analysis, and reproducible report generation.

The central result is honest rather than uniformly positive. Forge reduces IR
before standard pipelines and changes performance on some kernels, but effects
are workload-dependent. LLVM's broader scalar pipeline outperforms Forge on
several cases, and O2/O3 completely subsume Forge on the measured suite.

## Frozen methodology

- Toolchain: Ubuntu 24.04, LLVM/Clang 18.1.3, C++17.
- Workload seed: `20261013`.
- Tuning split: reduction, repeated expression, loop recurrence.
- Sealed evaluation split: dot product, stencil row, strided access, matrix
  multiply.
- Schedules: minimal, two Forge orders, comparable LLVM scalar, O2, O2+Forge,
  O3, and O3+Forge.
- Runtime protocol: 21 CPU-0-pinned rounds with seeded randomized schedule
  order and an untimed per-process warm-up.
- Outputs: raw trials, exact commands, host/toolchain metadata, validation
  digest, optimizer time, IR/assembly counts, binary size, artifact hashes,
  Markdown/SVG reports, and paired case studies.

The evaluation split was declared before the campaign. No learned or automatic
scheduler was added because current evidence does not support a robust policy.

## Diagnostics

`-forge-diagnostics-jsonl=<path>` enables versioned JSONL records per pass and
function. Records include instruction deltas, examined and eliminated
candidates, cross-block and loop activity, elapsed nanoseconds, and enumerated
rejection reasons. LLVM optimization remarks report successful transformations.
Diagnostics are opt-in and were not enabled inside benchmark timings.

## Correctness evidence

At checkpoint `0129f63`, the LLVM 18 CTest suite reported 13 passed, 2 skipped,
and 0 failed across 15 tests. Evidence includes structural FileCheck tests,
LLVM verifier checks, 100 generated modules, executable differential tests,
structured diagnostics, registry/report smoke tests, static backend generation,
and 250 deterministic mutation cases preserving failure artifacts.

The skipped tests are part of the result:

- Sanitized differential execution: SKIPPED because the cached local image
  lacks the Clang 18 sanitizer runtime. CI configuration installs it, but that
  CI run has not been observed on a pushed v3 commit.
- Alive2: SKIPPED because `alive-tv` is unavailable. The bridge records
  `unavailable`; Forge makes no formal-refinement claim.

Passing empirical tests is not proof for all LLVM IR. The accepted expression
domain remains integer binary operations with exact opcode, type, operands, and
semantic flags; memory operations, floating point, poison/undef-containing
constants, and version-sensitive `or disjoint` behavior remain excluded.

## Performance findings

The campaign of record is `20261014T195403Z-06973af`. All 1,176 observations
validated. Canonical Forge reduced aggregate IR from 524 to 512 instructions
and assembly from 819 to 817. Its paired intervals were neutral for five
kernels, lower for matrix multiply, and higher for stencil. LLVM scalar removed
more code and had lower-runtime intervals on four kernels, with three neutral.

Both Forge pass orders generated identical IR, assembly, and executables.
Appending Forge after O2 or O3 also generated byte-identical artifacts to the
corresponding baseline. All paired timing intervals for those identical-code
comparisons crossed 1.0, so no incremental Forge effect is claimed.

See [the full performance evidence](PERFORMANCE_REPORT.md) for exact ratios,
intervals, reproduction commands, and threats to validity.

## Architecture evidence

Static LLVM 18 code generation succeeded for x86-64-v3, AArch64 Neoverse V2,
and Armv9-A+SVE2. For three small kernels, the generated whole-file summaries
were:

| Target | Instructions | Vector-referencing | SVE | Distinct vector registers | Stack accesses |
|---|---:|---:|---:|---:|---:|
| x86-64-v3 | 152 | 76 | 0 | 13 | 0 |
| Neoverse V2 | 142 | 36 | 21 | 14 | 0 |
| Armv9-A+SVE2 | 154 | 45 | 45 | 9 | 0 |

`llvm-mca` reported aggregate model IPC 5.25 / block throughput 28.2 for the
x86-64 file and IPC 6.93 / throughput 11.0 for Neoverse V2. Cross-target values
are not directly comparable performance scores. Vector-register counts are
whole-file proxies rather than liveness analysis, stack accesses do not prove
spills, and AArch64 output was never executed on native hardware.

## Reproducibility and provenance

Forge v3 was developed as logical checkpoints on `feature/forge-v3-evidence`:

1. baseline and host audit;
2. structured pass diagnostics;
3. schedule registry and report generation;
4. differential, mutation, sanitizer, and formal bridges;
5. generated-code hashes and instruction counts;
6. randomized-interleaved measurement protocol;
7. paired case-study analysis; and
8. quantified static backend analysis.

Generated run directories are ignored because they include binaries and bulky
raw artifacts. Every report contains the producing commit and exact command;
the scripts reconstruct reports from manifests and CSV rather than relying on
manually curated speedup tables.

## Known gaps

- No observed Alive2 proof and no observed sanitizer run in the local image.
- No hardware counters, fixed-frequency lab setup, native AArch64, or Grace.
- No large application suite such as SPEC CPU; only seven deterministic
  kernels and three backend-analysis kernels.
- No memory value numbering, PRE, PHI translation, floating-point CSE, general
  loop unrolling, or automatic scheduler.
- No v3 branch push, pull request, remote CI result, or release artifact yet.

These gaps bound the claims. They are not converted into passing evidence.
